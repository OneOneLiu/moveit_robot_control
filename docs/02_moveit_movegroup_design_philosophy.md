# MoveIt MoveGroup Action 设计理念

## 问题

1. 按照 `moveit_msgs/action/MoveGroup` 的接口来看，这个 action 里最重要的反而是各种 constraints，为什么要这么设计？
2. 这个 action 的定义为什么这么长？它的设计理念是什么？
3. 为什么不拆成多个 action，比如关节运动用一个，笛卡尔用一个？

---

## 为什么 Constraints 是核心而不是"目标位置"

关键在于**运动规划本质上是一个约束满足问题**，而不是"从 A 到 B"的问题。

规划器的工作是：在关节空间里搜索一条路径，使得终点满足你给的约束，同时路上不碰东西。从这个角度看：

- "关节 1 转到 45°" = 一个关节约束
- "末端到 xyz" = 一个位置约束（需要 IK 求解哪些关节构型能满足它）
- "末端到 xyz 且保持姿态" = 位置约束 + 姿态约束

对规划器来说，这三种写法本质上是**同一件事**。`joint_constraints` 和 `position_constraints` 只是描述目标的不同语言，规划器最终都在关节空间里搜索。

这个设计带来的好处是**欠约束（under-constrained）很自然**：只填 `position_constraints` 不填 `orientation_constraints`，规划器就有自由度去选择末端姿态，在 7 轴机械臂上可以充分利用冗余自由度。如果拆成两个 action，"只约束位置不约束姿态"这件事就变得难以表达。

---

## 为什么不拆成多个 Action

**从规划器视角看，拆分是假区分。**

Pilz 的 `LIN` 规划器做笛卡尔直线运动，OMPL 做自由空间规划，它们接受同样的约束描述，只是内部求解方式不同。通过 `pipeline_id` 和 `planner_id` 来切换，不需要换 action server。如果拆成两个 action，选择哪个就变成了客户端的负担。

**混合约束是现实需求。** 真实任务里经常需要同时写：

```
goal_constraints:    末端到达目标位置
path_constraints:    整条路上末端保持朝下（防洒水）
planning_scene_diff: 路边临时有个障碍物
```

这三类约束天然属于同一次规划请求，拆开就没法组合了。

**场景管理只有一套。** 碰撞检测、规划场景、IK 求解都在 MoveGroup 节点里统一维护。如果有多个 action server，每个都要独立处理这些，要么重复，要么共享状态引发竞争。

---

## Action 为什么这么长

长度来自于它把**所有可能用到的上下文一次性打包进请求**，而不是靠多次交互拼凑。

一次完整的规划请求需要回答这些问题：

```
目标是什么？       → goal_constraints
路上有什么限制？   → path_constraints
世界里有什么障碍？ → planning_scene_diff
机器人现在在哪？   → start_state
用什么规划器？     → pipeline_id / planner_id
规划多久算超时？   → allowed_planning_time
失败了要怎么办？   → replan / replan_attempts
只规划还是要执行？ → plan_only
```

如果把这些拆成多个接口（先设置场景、再设置约束、再触发规划），就需要维护状态机，出错时很难判断哪一步的状态不对。一个长请求 = 一次原子操作，要么整体成功，要么整体失败，调试更清晰。

---

## 类比总结

可以把这个 action 理解成一个**声明式的规划请求**：你描述"终态应该满足什么"，而不是"怎么走到那里"。这和 SQL 的设计理念类似——你写 `WHERE` 条件，数据库自己决定怎么查。规划器自己决定走关节空间还是笛卡尔空间，选哪条路径，只要最终满足你的约束就行。
